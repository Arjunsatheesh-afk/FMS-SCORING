# Python dependencies for the FMS scoring backend.
#
# ONE file covers both platforms, using PEP 508 environment markers rather than
# a requirements-win.txt / requirements-linux.txt pair. Two files would need
# every shared pin kept in step by hand, and this differs on four lines.
#
#   Windows (x86_64, Python 3.11-3.13)  - the development machine
#   Linux   (x86_64, Python 3.11-3.13)  - where the original freeze was taken
#
# macOS is NOT covered, and neither is Linux on ARM: the CUDA runtime packages
# below publish no wheels for either.
#
# INSTALL - all three steps. Do not stop after the first.
#
#     python -m venv .venv
#     .venv/Scripts/python -m pip install -r requirements.txt     # Windows
#     .venv/bin/python     -m pip install -r requirements.txt     # Linux
#
#     python -m pip uninstall -y onnxruntime
#     python -m pip install --force-reinstall --no-deps onnxruntime-gpu==1.24.4
#
# Then CHECK, because the failure this guards against is silent:
#
#     python -c "import onnxruntime as o; print(o.__version__)"
#
# Expected 1.24.4. If it prints 1.29.0, step 2 did not happen and the CPU
# package has won.
#
# Do NOT use onnxruntime.get_available_providers() as the GPU check. It lists
# providers COMPILED IN, not providers that can actually load: on a correct
# install of this project it reports CUDAExecutionProvider while a bare
# InferenceSession still falls back to CPU, because the CUDA DLLs shipped by
# the nvidia-* wheels are not on the Windows DLL search path by default. The
# pipeline handles that itself - build_detector() calls
# _configure_windows_cuda_dll_paths() before importing rtmlib - so the honest
# end-to-end check is the pipeline's own entry point:
#
#     python -c "from fms_pipeline import build_detector, _detector_session_providers; \
#                d, dev = build_detector('balanced', 'cuda'); \
#                print(dev, _detector_session_providers(d))"
#
# Expected: cuda, with CUDAExecutionProvider in every session's list. This
# downloads the RTMPose models on first run.
#
# Why steps 2 and 3 exist: rtmlib 0.0.15 hard-requires the CPU `onnxruntime`
# distribution, so pip installs it ALONGSIDE onnxruntime-gpu. Both ship the
# same `onnxruntime` module, pip writes the CPU one last, and CUDA disappears
# with no error at all - measured on a clean venv here, which came up reporting
# 1.29.0 and ['AzureExecutionProvider', 'CPUExecutionProvider']. A requirements
# file cannot express "skip this transitive dependency", which is why this is a
# documented step rather than a line below.
#
# Afterwards `pip check` reports "rtmlib requires onnxruntime, which is not
# installed". That warning is EXPECTED and is the correct end state - the
# working .venv has read exactly that all along. onnxruntime-gpu provides the
# module rtmlib actually imports.
#
# GPU note, because it is not what it looks like: torch here is the CPU build
# (it resolves to 2.10.0+cpu on Windows) and torch.cuda.is_available() is False.
# That is correct and not a broken install. The pose pipeline runs on
# onnxruntime-gpu's CUDAExecutionProvider, not on torch, so no extra package
# index is needed - everything below comes from PyPI.
#
# If you bump the onnxruntime-gpu pin below, bump it in step 2 as well.
#
# Four packages carry a marker. They are torch's own Linux CUDA dependencies -
# torch 2.10.0 declares them with exactly the marker used here - and they
# publish no Windows wheels and no sdist at all, so an unmarked pin makes the
# whole file fail to resolve on Windows. That is why this file was unusable
# here and the working .venv had to be assembled by hand.
